# Администрирование

Административные страницы открываются только для роли `admin`. Возможности вроде
`users.manage` уже есть в модели, но HTTP-маршруты пока их не проверяют.

Основное административное меню находится в **Control** и включает пользователей,
сценарии, Golden Images и доступ.

## Пользователи

В **Control -> Users** можно создать пользователя, изменить его имя, пароль, роли,
команды и состояние, а также удалить его.

Особенности:

- логин уникален и после создания в форме не меняется;
- новый пароль обязателен;
- если API создания получит пустой пароль в обход браузерной проверки, будет использован `changeme`;
- при редактировании пустое поле пароля оставляет старый хеш;
- выключенный пользователь не может войти и не проходит проверку существующей сессии;
- удалить самого себя через интерфейс нельзя;
- удаление пользователя не удаляет историю его запусков каскадом.

Аутентификация сейчас только локальная. Поле `auth_source` уже есть в модели, но LDAP ещё не подключён.

## Роли

Роль собирает возможности и может наследовать другие роли. Наследование обходится рекурсивно, а повторно встреченная роль пропускается. Цикл запрос не повесит, но полезного смысла у такого наследования нет.

Системные роли создаются при старте:

| Роль | Возможности |
|---|---|
| `admin` | все системные возможности и обход ACL |
| `developer` | просмотр и запуск сценариев |
| `tester` | просмотр и запуск сценариев |

Форма сохраняет роль по slug: повторная отправка существующего slug обновит имя, описание, наследование и полный набор возможностей.

## Команды

Команда задаёт продуктовую область и используется как вторая ось ACL. Пользователь хранит ID команд, а ACL может ссылаться как на числовой ID, так и на slug — проверка понимает оба варианта.

При старте создаются команды `frontend`, `backend` и `protocol`, если их ещё нет.

## Сценарии и компоненты

На странице сценариев можно:

- создать или изменить компонент;
- удалить неиспользуемый компонент;
- создать сценарий;
- открыть YAML-редактор существующего сценария;
- изменить slug сценария;
- назначить ACL;
- просмотреть версии и восстановить старую;
- импортировать или экспортировать YAML.

Серверная проверка при сохранении требует `label`, `component`, непустой `steps`, а у каждого шага — `id`, `spider`, `action` и уникальный ID. Браузерный редактор проверяет больше полей для ранней подсветки ошибок; сервер всё равно валидирует запрос отдельно.

## Golden Images

Страница **Control -> Golden Images** связывает понятные Arachne-профили с реальными Proxmox QEMU templates.

Администратор задаёт только:

- красивое имя профиля;
- стабильный ключ;
- семейство ОС;
- выбранный Proxmox template;
- enabled/disabled.

Пример:

```text
Name:     RedOS 8
Key:      redos8
OS:       RedOS 8
Template: redos8-golden · #9002 · pve01
```

### Что показывается автоматически

После выбора template карточка профиля показывает live metadata, полученные из Proxmox:

- VM ID;
- node;
- CPU;
- RAM;
- системный диск;
- размер диска;
- interface;
- datastore.

Эти поля нельзя редактировать в Arachne. Если нужно изменить их, меняйте template в Proxmox. При следующем открытии страницы и следующем provision spider увидит фактические новые значения.

### Почему так

Arachne не должна хранить вторую копию конфигурации Proxmox. PostgreSQL отвечает только за соответствие `profile -> template VM ID`, а реальная конфигурация VM остаётся в Proxmox.

Это значит, что перенос template на другой node или storage не требует правки `.env`.

### Несколько образов одного семейства

Можно создать несколько профилей:

```text
redos8
redos8-clean
redos8-ad
windows
windows-term
```

В обычном сценарии `os: redos8` использует профиль `redos8`. Конкретный образ выбирается через `image`:

```yaml
with:
  os: redos8
  image: redos8-clean
```

### Broken profile

Если выбранный VM ID исчез, перестал быть template или перестал быть доступен сервисному токену, профиль не удаляется. Карточка переходит в состояние broken.

Это важно: сломанное соответствие должно быть видно администратору. Новый provision через broken profile блокируется до исправления mapping или доступа.

### Замена golden image

Чтобы заменить основной образ без изменения сценариев:

1. подготовьте новый Proxmox template;
2. убедитесь, что он отображается в Golden Images;
3. переключите существующий профиль, например `redos8`, на новый VM ID;
4. проверьте карточку;
5. новые VM будут клонироваться из нового template.

Уже созданные стенды остаются управляемыми. Их backend metadata сохранены в `managed_machines`, поэтому destroy не зависит от текущего mapping профиля.

Полная эксплуатационная инструкция: [Golden Images](/ru/operations/golden-images).

## Первоначальный администратор

Пользователь `admin` создаётся только при отсутствии такого логина. Его пароль берётся из `ADMIN_PASSWORD`, а при отсутствии переменной — из небезопасного значения `admin`. После появления записи изменение переменной пароль не обновляет.
