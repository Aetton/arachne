# Роли и доступ

Доступ в Arachne состоит из двух этажей:

1. роль должна содержать системную возможность;
2. ACL конкретного сценария должен разрешить действие этой роли и/или команде.

Доступ открывается после обеих проверок. Роль `admin` проходит напрямую.

## Системные возможности

| Slug | Назначение |
|---|---|
| `scenarios.view` | видеть сценарии |
| `scenarios.run` | запускать сценарии |
| `scenarios.create` | создавать сценарии |
| `scenarios.edit` | редактировать черновики |
| `scenarios.publish` | публиковать версии |
| `scenarios.delete` | выключать сценарии |
| `scenarios.manage_acl` | управлять ACL |
| `roles.manage` | управлять ролями и командами |
| `users.manage` | управлять пользователями |

Пользовательские страницы применяют `scenarios.view` и `scenarios.run`.
Административные маршруты пока проверяют только роль `admin`. Остальные возможности
из таблицы уже есть в модели, однако HTTP-слой их ещё не использует.

## ACL сценария

У записи ACL есть:

- действие: `view`, `run`, `edit` или `manage`;
- субъект: `role` или `team`;
- ключ субъекта: slug роли, ID или slug команды;
- эффект: `allow` или `deny`;
- режим: `all` или `any`.

Без подходящей записи ACL доступ запрещён: здесь действует принцип default deny.

## `all` и `any`

При `all` пользователь должен совпасть по каждой непустой оси:

```yaml
access:
  run:
    match: all
    roles: [developer]
    teams: [backend]
```

Такой сценарий запустит только разработчик из backend-команды.

При `any` достаточно совпасть с ролью или командой:

```yaml
access:
  view:
    match: any
    roles: [tester]
    teams: [backend]
```

Если в ACL присутствует только одна ось, пустая ось считается совпавшей. Поэтому
`all` с одними ролями работает как обычный список ролей.

## Запреты и точный формат ACL

Запись с `effect: deny` имеет приоритет над разрешениями для совпавшего пользователя.
Точный формат `access_rules` уже поддерживается **атомарным YAML-импортом**,
хотя упрощённый `access` и административная форма ориентированы на разрешения.

Пример ACL, включаемого в описание сценария при импорте:

```yaml
access_rules:
  - subject_type: role
    subject_key: developer
    permission: run
    effect: allow
    match_mode: any
  - subject_type: team
    subject_key: restricted
    permission: run
    effect: deny
    match_mode: any
```

Все пять полей обязательны. `subject_type`: `role` или `team`;
`permission`: `view`, `run`, `edit`, `manage`;
`effect`: `allow` или `deny`; `match_mode`: `all` или `any`.
Нельзя одновременно передавать `access` и `access_rules`.
Явное `access_rules: []` при обновлении очищает ACL.
Администратор обходит сценарный ACL.

Подробнее: [импорт сценариев](/ru/user-guide/scenarios#атомарный-yaml-импорт).

### Особенности административной формы

Seed YAML в старом формате обычно записывает команду по slug, а административная
форма использует числовой ID. После открытия такого ACL команда может выглядеть
неотмеченной. Перед сохранением проверьте состав прав.

Если при создании сценария не переданы роли и команды, Arachne назначает
разрешения ролям и командам создателя. Пустой ACL у существующего сценария
закрывает доступ всем, кроме администратора.

## ACL при создании

Если при создании сценария форма не передала ни одной роли или команды, Arachne
назначает все четыре действия ролям и командам создателя. Для администратора без
команд это обычно создаёт записи на роль `admin`, хотя сам администратор всё равно
обходит ACL.

Если снять все галочки у существующего сценария и сохранить его, ACL станет пустым,
и не-администраторы потеряют доступ.
