## Оставшиеся проблемы по приоритетам

### P1. Неограниченный runtime-журнал

**Факт:** `api/run_engine.py` хранит все строки в `_live[run_id]`, в конце выполняет `list(_live[run_id])` и `json.dumps(live)` в `Run.log` (`Text`). Передача длинного журнала в целую JSON-строку создаёт несколько копий данных в памяти. При ошибке записи в БД runtime намеренно остаётся в памяти.

**Риск:** рост RSS пропорционально объёму логов, скачки памяти при сериализации, длительные транзакции/дорогие чтения. Это подтверждённый архитектурный риск; конкретная доля RSS в проде не измерялась.

**План:** append-only записи лога в отдельную таблицу с `run_id/seq/step_id/stream`, batched INSERT и серверная пагинация; последние N строк оставить в bounded ring buffer для SSE. Запись журнала не должна зависеть от успешного завершения run.

### P1. Отсутствует контракт миграции секретов

**Факт:** `save_credential` раньше при изменении provider/ref читала секрет из *нового* хранилища, а не переносила старый, после чего меняла указатель. PR #130 блокирует такое изменение, но не реализует migration.

**План:** отдельная операция `Move credential` с проверкой зависимостей, записью нового payload, перепривязкой по стабильной ID, проверкой результата и безопасным удалением старого ref. Операции над Vault и PostgreSQL нельзя считать одной ACID-транзакцией: нужны этапы и компенсация.

### P1. Неполная проверка реальных интеграций

**Факт:** прошедшие 105 тестов преимущественно unit/HTTP с SQLite/mocks; `tofu-schema` проверяет только схему oVirt. Реальный oVirt 401 не закрыт, работа с TLS и CA на живом oVirt/Proxmox не подтверждена тестами.

**План:** отдельный opt-in integration suite на тестовом контуре; healthchecks и проверки API должны проходить тем же клиентом, что Golden Images, без записи секретов в логи.

### P2. Схема БД меняется из runtime-кода

**Факт:** `api/database.py::init_db()` вызывает `Base.metadata.create_all()`; `api/secrets_store.py` и `api/golden_images.py` вызывают `ensure_schema()`, а Golden Images проверяет и дополняет колонки из работающего приложения. При этом проект уже использует Alembic.

**Риск:** гонки на старте нескольких процессов, трудное восстановление истории схемы, незаметные различия между fresh install и upgrade.

**План:** только Alembic отвечает за DDL; код приложения проверяет версию схемы и падает с точной ошибкой, но не делает `ALTER TABLE` во время обычных запросов.

### P2. Plugin loader приводит к общему падению API

**Факт:** `api/core/registry.py::load_plugins()` импортирует модули рекурсивно. Уже был реальный инцидент: SyntaxError в `connection_tests.py` мешал загрузить `infrastructure_admin.py` и запуску всего сервера.

**План:** compile/import smoke test всех активируемых модулей в CI и перед сборкой образа; затем разделить обязательные компоненты и опциональные runtime-спайдеры. Не скрывать ошибки обязательных модулей молчаливым continue.

### P2. Разная семантика шины

**Факт:** `NatsBus.request()` ловит все исключения и возвращает `{"error": ...}`; `InMemoryBus.request()` по-разному обрабатывает timeout и исключение обработчика. NATS callbacks не оформлены единым перехватом ошибок.

**План:** одинаковая схема ошибки `code/message/context` в обеих реализациях, contract tests для success/timeout/no-responder/exception/cancel.

### P2. Фронтенд загружает библиотеки с публичных CDN

**Факт:** `frontend/templates/base.html` подключает Tailwind через CDN, HTMX и Tabler icons с публичных доменов. Изолированный корпоративный браузер может их не получить.

**План:** vendoring статических зависимостей в `frontend/static/`, фиксированные версии, сборка без доступа браузера к внешнему интернету. Не делать редизайн ради этого.

### P2. Тестов Jinja недостаточно для интерфейса

**Факт:** часть фронтенд-тестов проверяет наличие HTML-фрагментов, но не поведение контролов в браузере. Сломанный combobox Golden Images прошёл такие проверки.

**План:** несколько браузерных smoke flows для создания/edit/delete credential, CA dialog, Golden Images и динамических инпутов. Не нужно тестировать каждый пиксель.

## Предложенный порядок

1. Влить #129, затем #130 после ревью; проверить текущий deploy и scheduler.
2. Снять профиль RSS на длинном реальном сценарии и внедрить bounded logs/persisted chunks.
3. Избавиться от runtime DDL и закрепить путь миграций.
4. Унифицировать ошибки и connection probes, устранить oVirt 401 на тестовом контуре.
5. Добавить минимальные браузерные smoke tests и локальные frontend assets.
6. Уже затем рефакторить инфраструктурные адаптеры. Без новой абстракции там, где достаточно трёх функций.
